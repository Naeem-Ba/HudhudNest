# برومبت تنفيذ Phase 4 — Responsive QA and Release Gate

أنت مهندس QA وFrontend خبير في Angular وCapacitor وواجهات RTL/LTR. نفّذ مرحلة اختبار عملية فوق Phase 1–3 دون إدخال Visual Regression أو إطار E2E ثقيل في مشروع ذي تغطية منخفضة.

## الهدف
تحويل التحسينات المتجاوبة إلى عملية قابلة للتكرار والمراجعة، بحيث لا تُعتبر أي صفحة من صفحات Phase 3 منتهية دون اختبار موثق على عروض 375px و768px و1440px، ولا يُدمج أو يُصدر أي تغيير UI/Capacitor دون بوابة واضحة.

## النطاق الإلزامي
1. أنشئ مصفوفة اختبار يدوية ثابتة للصفحات النشطة التالية:
   - Home وNavbar.
   - قائمة العقارات.
   - تفاصيل العقار.
   - Login/Register.
   - نموذج إضافة/تعديل العقار.
   - Profile.
   - Favorites.
   - Notifications.
2. استخدم ثلاثة عروض فقط: 375px، 768px، 1440px.
3. لكل صفحة اختبر: overflow، layout، النصوص، الصور، touch targets، keyboard، RTL/LTR، loading/error/empty states حيث تنطبق.
4. أضف قالب Pull Request يحتوي بنداً صريحاً: `تم الاختبار على 375/768/1440px`، مع مساحة لتوثيق النتيجة والأدلة.
5. أضف بوابة إصدار لأي تغيير UI/Capacitor تتطلب اختبار جهاز حقيقي واحد على الأقل، وتشدد على Android الفعلي واختبار iPhone عند توفر منصة iOS.
6. لا تدّع تنفيذ اختبار جهاز حقيقي داخل بيئة لا تملك جهازاً.
7. لا تضف Playwright/Cypress أو Visual Regression في هذه المرحلة.
8. لا تعدّل منطق الأعمال أو تصميم الصفحات.

## معايير الجودة
- الملفات قابلة للنسخ مباشرة إلى المستودع.
- قائمة التحقق قصيرة بما يكفي لتُستخدم فعلياً، لكنها تغطي المخاطر الأعلى.
- يميّز التوثيق بين Browser viewport testing وNative device testing.
- يحدد بوضوح متى يمنع الدمج ومتى يمنع الإصدار.
- يقدم قالباً موحداً لتسجيل الجهاز، النظام، الاتجاه، النتيجة، والدليل.
