# Phase 4 — الاختبار اليدوي وبوابة إصدار UI

## ما نُفّذ

أُضيفت عملية QA خفيفة وقابلة للتطبيق بدلاً من إدخال Visual Regression أوE2E ثقيل في مشروع ذي تغطية اختبار منخفضة.

### الملفات

- `docs/RESPONSIVE-MANUAL-TEST-MATRIX.md`: مصفوفة الصفحات عند 375/768/1440.
- `docs/UI-RELEASE-GATE.md`: شروط منع الدمج ومنع الإصدار واختبار الجهاز الحقيقي.
- `.github/pull_request_template.md`: قالب PR يفرض توثيق القياسات واللغات والأدلة.
- `docs/PHASE-4-IMPLEMENTATION-PROMPT.md`: البرومبت التنفيذي المستخدم.

## القرارات

1. لم تتم إضافة Playwright أوCypress أوVisual Regression، لأن ذلك خارج الهدف الحالي وسيضيف بنية صيانة قبل استقرار الأساس.
2. تم تثبيت ثلاثة عروض فقط لتقليل كلفة التنفيذ ومنع قوائم تحقق لا يستخدمها الفريق.
3. الاختبار عند 375/768/1440 هو شرط دمج للصفحات المتأثرة.
4. الاختبار على جهاز Android أوiPhone حقيقي هو شرط إصدار لأي تغيير UI/Capacitor.
5. لا يمكن اعتبار DevTools دليلاً على Safe Area أوHardware Back أوسلوك keyboard.
6. لم يُدّع تنفيذ اختبار جهاز فعلي داخل بيئة المراجعة.

## طريقة الاستخدام اليومية

### عند فتح Pull Request

1. حدد الصفحات المتأثرة.
2. افتح `docs/RESPONSIVE-MANUAL-TEST-MATRIX.md`.
3. اختبر الصفحات عند 375px و768px و1440px.
4. نفّذ دورة RTL ودورة LTR.
5. املأ جدول قالب PR وأرفق الأدلة عند وجود مشكلة أوتغيير بصري مهم.

### قبل الإصدار

1. ابنِ التطبيق وSync منصة Capacitor.
2. اختبر جهازاً فعلياً واحداً على الأقل.
3. نفّذ Safe Area وHardware Back وKeyboard وPortrait/Landscape.
4. املأ سجل الجهاز في `docs/UI-RELEASE-GATE.md` أوانسخه إلى تذكرة الإصدار.

## حدود التنفيذ

هذه المرحلة تضيف آلية اختبار وتوثيق فقط. لا يمكن لهذه البيئة تنفيذ اختبار فعلي على هاتف غير متصل، لذلك يجب إكمال بنود الجهاز محلياً قبل الإصدار.
